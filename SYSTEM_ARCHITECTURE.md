## 1. DATABASE SCHEMA (FINAL & CLEAN)

### 1.1 USERS TABLE
```sql
users (from Supabase Auth - DO NOT recreate)
- id (UUID) - Primary Key
- email (string) - Unique
- phone (string) - OPTIONAL for users
- is_admin (boolean) - DEFAULT FALSE (only abdulsist23@gmail.com = TRUE)
- created_at (timestamp)
- updated_at (timestamp)
```

**RLS Policy:**
- Users can only read their own phone number
- Admins can read all phone numbers
- Email never shown to users


### 1.2 EVENTS TABLE
```sql
CREATE TABLE events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(255) NOT NULL,
  description TEXT,
  date DATE NOT NULL,
  location VARCHAR(255),
  max_teams INT NOT NULL,
  registration_fee DECIMAL(10, 2) NOT NULL,
  is_active BOOLEAN DEFAULT TRUE,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW()
);
```

**RLS Policy:**
- Public can read active events
- Only admins can create/edit events


### 1.3 TEAMS TABLE
```sql
CREATE TABLE teams (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  event_id UUID NOT NULL REFERENCES events(id) ON DELETE CASCADE,
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  team_name VARCHAR(255) NOT NULL,
  phone_number VARCHAR(15) NOT NULL,
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW(),
  
  UNIQUE(event_id, user_id) -- ONE team per user per event
);
```

**RLS Policy:**
- Users can read/create their own teams
- Admins can read all teams
- Users cannot update/delete teams (to prevent cheating)


### 1.4 TEAM_MEMBERS TABLE
```sql
CREATE TABLE team_members (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  team_id UUID NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
  member_name VARCHAR(255) NOT NULL,
  member_email VARCHAR(255),
  member_phone VARCHAR(15),
  created_at TIMESTAMP DEFAULT NOW()
);
```

**RLS Policy:**
- Users can read members of their own teams
- Admins can read all members
- Users cannot modify members (team is locked after creation)


### 1.5 REGISTRATIONS TABLE
```sql
CREATE TABLE registrations (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  team_id UUID NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
  event_id UUID NOT NULL REFERENCES events(id) ON DELETE CASCADE,
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  status VARCHAR(50) DEFAULT 'ACTIVE', -- ACTIVE, CANCELLED, etc.
  created_at TIMESTAMP DEFAULT NOW(),
  
  UNIQUE(team_id) -- ONE registration per team
);
```

**RLS Policy:**
- Users can read their own registrations
- Admins can read all registrations


### 1.6 PAYMENTS TABLE (MANUAL VERIFICATION)
```sql
CREATE TABLE payments (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  team_id UUID NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
  event_id UUID NOT NULL REFERENCES events(id) ON DELETE CASCADE,
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  
  -- Payment Details
  amount DECIMAL(10, 2) NOT NULL,
  transaction_id VARCHAR(255),
  payment_screenshot_url VARCHAR(500),
  
  -- Status: PENDING → WAITING_FOR_ADMIN_CONFIRMATION → APPROVED or REJECTED
  status VARCHAR(50) DEFAULT 'PENDING',
  
  -- Admin Decision
  admin_id UUID REFERENCES auth.users(id),
  admin_comment TEXT,
  admin_decision_at TIMESTAMP,
  
  created_at TIMESTAMP DEFAULT NOW(),
  updated_at TIMESTAMP DEFAULT NOW(),
  
  UNIQUE(team_id) -- ONE payment per team
);
```

**Status Lifecycle:**
- PENDING: User hasn't uploaded screenshot/transaction yet
- WAITING_FOR_ADMIN_CONFIRMATION: User submitted proof, awaiting admin review
- APPROVED: Admin approved, ticket can be generated
- REJECTED: Admin rejected, final decision, user cannot re-submit

**RLS Policy:**
- Users can read/insert their own payments
- Users cannot update payments (only admin can)
- Admins can read/update all payments
- Payment screenshot URL stored in Supabase Storage (private)


### 1.7 TICKETS TABLE (AUTO-GENERATED BY ADMIN APPROVAL)
```sql
CREATE TABLE tickets (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  team_id UUID NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
  event_id UUID NOT NULL REFERENCES events(id) ON DELETE CASCADE,
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  payment_id UUID NOT NULL REFERENCES payments(id) ON DELETE CASCADE,
  
  ticket_code VARCHAR(255) UNIQUE NOT NULL,
  qr_code_url VARCHAR(500) NOT NULL,
  ticket_pdf_url VARCHAR(500),
  
  created_at TIMESTAMP DEFAULT NOW(),
  
  UNIQUE(team_id) -- ONE ticket per team
);
```

**RLS Policy:**
- Users can read their own tickets
- Admins can read all tickets
- Users cannot modify tickets


### 1.8 AUDIT_LOG TABLE (SECURITY)
```sql
CREATE TABLE audit_log (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  admin_id UUID NOT NULL REFERENCES auth.users(id),
  action VARCHAR(100) NOT NULL, -- APPROVED_PAYMENT, REJECTED_PAYMENT, etc.
  payment_id UUID REFERENCES payments(id),
  details JSONB,
  created_at TIMESTAMP DEFAULT NOW()
);
```

**RLS Policy:**
- Only admins can read audit logs

## 2. USER FLOW (DETAILED)

### Step 1: LOGIN
```
User navigates to /login
↓
Checks: Is user logged in? (via Supabase Auth)
  ✅ YES → Skip to Step 2
  ❌ NO → Show login form
↓
User logs in via Supabase Auth
↓
Redirect to /events
```

**Protection:**
- ALL pages check `supabase.auth.getSession()`
- If NO session → Redirect to /login


### Step 2: SELECT EVENT & REGISTER
```
URL: /events
Page loads → Fetch all active events from DB
↓
User clicks on an event
↓
Redirect to /register/:eventId
↓
Check: Is user logged in?
  ✅ YES → Show registration form
  ❌ NO → Redirect to /login
↓
User enters:
  - Team name
  - Team members (name, email, phone)
  - Phone number (MANDATORY - for admin to call)
↓
User clicks REGISTER
```

**Database operations:**
1. Create TEAM record
2. Create TEAM_MEMBERS records
3. Create REGISTRATION record (status = ACTIVE)
4. Create PAYMENT record (status = PENDING, amount = event.registration_fee)
5. Return payment.id

**Response:**
```
Redirect to /payment/:paymentId
```

**Validations:**
- No duplicate teams per user per event (DB constraint)
- All fields mandatory
- Phone format validated


### Step 3: PAYMENT PAGE
```
URL: /payment/:paymentId
↓
Check: Is user logged in?
  ✅ YES → Continue
  ❌ NO → Redirect to /login
↓
Fetch payment record from DB
  Check: payment.user_id === currentUser.id?
    ✅ YES → Show payment page
    ❌ NO → Show 404 (not their payment)
↓
Page shows:
  - UPI QR Code (image)
  - Bank Account details
  - "Transfer amount: ₹{amount}"
  - Payment screenshot upload form (MANDATORY)
  - Transaction ID input (MANDATORY)
↓
User uploads screenshot → Store in Supabase Storage (private bucket)
User enters transaction ID
↓
User clicks SUBMIT
```

**Database update:**
```sql
UPDATE payments 
SET 
  status = 'WAITING_FOR_ADMIN_CONFIRMATION',
  transaction_id = user_input,
  payment_screenshot_url = storage_url,
  updated_at = NOW()
WHERE id = paymentId AND user_id = currentUser.id
```

**Response:**
```
Show message: "Payment submitted. Waiting for admin confirmation."
↓
Redirect to /ticket/:paymentId (but show message: Ticket will appear after approval)
OR
Redirect to /myregistrations (show status = WAITING_FOR_ADMIN_CONFIRMATION)
```

**Validations:**
- Screenshot file size < 5MB
- Transaction ID not empty
- User can only submit once (prevent re-upload)


### Step 4: WAIT FOR ADMIN
```
User views /myregistrations
↓
Shows all their registrations with status:
  - PENDING (no payment submitted yet)
  - WAITING_FOR_ADMIN_CONFIRMATION (admin reviewing)
  - APPROVED (ticket available)
  - REJECTED (final, cannot re-submit)
```

**User CANNOT:**
- Re-upload payment
- Modify transaction ID
- Bypass admin decision


### Step 5: AFTER ADMIN APPROVAL - TICKET PAGE
```
URL: /ticket/:paymentId
↓
Check: Is user logged in?
  ✅ YES → Continue
  ❌ NO → Redirect to /login
↓
Fetch payment record
  Check: payment.status === APPROVED?
    ✅ YES → Fetch ticket, show ticket page
    ❌ NO (PENDING/WAITING/REJECTED) → Show message "Ticket not available"
↓
Ticket shows:
  - Ticket Code
  - QR Code (generated by admin)
  - Event name
  - Team name
  - Transaction ID
  - Download PDF button
```

**Reload safety:**
- All data from DB
- No sessionStorage
- No 404 errors
- Page always accessible if user owns it

### Admin Dashboard
```

↓
Display table:
  | Event | Team | Phone | Transaction ID | Amount | Screenshot | Action |
  |-------|------|-------|----------------|--------|------------|--------|
  
For each payment:
  - Event name (from events table)
  - Team name (from teams table)
  - User phone (from teams table) - VISIBLE ONLY TO ADMIN
  - Transaction ID (from payments table)
  - Amount (from payments table)
  - Screenshot (clickable link to view in Supabase Storage)
```

**Admin Actions:**

### 1️⃣ APPROVE PAYMENT
```
Admin clicks [APPROVE]
↓
1. Update payments table:
   UPDATE payments
   SET 
     status = 'APPROVED',
     admin_id = currentAdmin.id,
     admin_decision_at = NOW()
   WHERE id = paymentId
   
2. Generate ticket:
   - ticket_code = unique_code (e.g., "ROBO2026-TEAM-{hash}")
   - qr_code_url = generate_qr_code(ticket_code)
   - Insert into tickets table
   
3. Log action:
   INSERT INTO audit_log
   (admin_id, action, payment_id, details)
   VALUES (adminId, 'APPROVED_PAYMENT', paymentId, {...})
   
4. Send email to user:
   Subject: "Payment Approved - Ticket Ready"
   Body: "Your ticket is ready. Download here: {ticket_link}"
   
5. Redirect back to /admin dashboard
```


### 2️⃣ REJECT PAYMENT
```
Admin clicks [REJECT]
↓
Optional: Admin enters reason in modal
↓
1. Update payments table:
   UPDATE payments
   SET 
     status = 'REJECTED',
     admin_id = currentAdmin.id,
     admin_comment = optional_reason,
     admin_decision_at = NOW()
   WHERE id = paymentId
   
2. Log action:
   INSERT INTO audit_log
   (admin_id, action, payment_id, details)
   
3. Send email to user:
   Subject: "Payment Rejected"
   Body: "Your payment was rejected. Reason: {admin_comment}"
   
4. Redirect back to /admin dashboard
```

**Important:** After rejection, user CANNOT re-upload. Decision is final.


### Admin Can Also:
- View all events
- View all teams
- View all users (phone numbers)
- View audit log
- Resend confirmation email to user

## 7. EDGE CASES & HANDLING

### Case 1: User refreshes /payment page
```
✅ CORRECT BEHAVIOR:
  - Fetch payment record from DB
  - If payment.user_id === currentUser.id → Show payment page
  - If not → 404
  - Data persists, no 404 errors
  - User can upload screenshot again (replace old one)
```

### Case 2: User tries to access /ticket/:paymentId before payment approved
```
✅ CORRECT BEHAVIOR:
  - Fetch payment record
  - Check: payment.status === APPROVED?
  - If NO → Show message: "Ticket not available yet. Status: WAITING_FOR_ADMIN_CONFIRMATION"
  - Do NOT throw 404
  - User can return later
```

### Case 3: User tries to register for same event twice
```
✅ CORRECT BEHAVIOR:
  - Database constraint: UNIQUE(event_id, user_id) on teams table
  - Prevent duplicate team creation
  - Show error: "You've already registered for this event"
```

### Case 4: User tries to upload payment twice
```
✅ CORRECT BEHAVIOR:
  - Check: payment.status === PENDING?
  - If YES → Allow update (replace old screenshot)
  - If status is WAITING/APPROVED/REJECTED → Disable upload button
  - Show message: "Payment already submitted"
```

### Case 5: Admin approves, then tries to reject
```
✅ CORRECT BEHAVIOR:
  - Once status = APPROVED, ticket is created
  - Admin CAN update status back to REJECTED (with reason)
  - Ticket record is NOT deleted (for audit)
  - But user cannot download ticket
  - User is notified of rejection
```

### Case 6: Two users try to access same payment
```
✅ CORRECT BEHAVIOR:
  - /payment/:paymentId checks: payment.user_id === currentUser.id
  - If different users → Show 404
  - Database RLS also prevents access
  - DOUBLE PROTECTION
```

### Case 7: Reloading /admin dashboard
```
✅ CORRECT BEHAVIOR:
  - Fetch fresh data from DB
  - Re-render all payments with WAITING status
  - No state loss
  - No 404 errors
  - Admin can work safely
```

### Case 8: User logs out mid-payment
```
✅ CORRECT BEHAVIOR:
  - User clicks logout
  - Session cleared
  - Redirect to /login
  - Payment record stays in DB (not lost)
  - User can log back in and resume from /payment/:paymentId
```

### Case 9: Payment screenshot upload fails
```
✅ CORRECT BEHAVIOR:
  - Show error message: "Upload failed. Try again."
  - Retry button
  - Do NOT change payment status
  - Payment stays PENDING
```

### Case 10: Admin forgets to add reason for rejection
```
✅ CORRECT BEHAVIOR:
  - admin_comment is OPTIONAL
  - If left empty, just say "Payment rejected"
  - Email user with minimal message
```
